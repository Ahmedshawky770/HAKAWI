# Authentication Architecture
## Hakawi Security Architecture

This document defines the authentication architecture for Hakawi, including session management, token lifecycle, MFA, and OAuth provider integration.

---

## Authentication Flow

### High-Level Flow
```
1. User initiates authentication (login/register)
2. Frontend redirects to OAuth provider OR accepts credentials
3. OAuth provider redirects back with authorization code
4. Backend exchanges code for access token
5. Backend creates/updates user record
6. Backend creates session (JWT + refresh token)
7. Frontend stores tokens securely
8. Frontend includes access token in API requests
9. Backend validates access token on each request
10. Frontend refreshes access token when expired
```

## Session Management

### Token Types

#### Access Token
- **Type:** JWT
- **Expiry:** 15 minutes
- **Storage:** Memory (frontend)
- **Payload:** `sub`, `accountType`, `adminRole`, `iat`, `exp`
- **Algorithm:** HS256

#### Refresh Token
- **Type:** Random secure string
- **Expiry:** 7 days
- **Storage:** HTTP-only secure cookie
- **Rotation:** Yes, on each refresh
- **Storage (backend):** Valkey with TTL

### Token Lifecycle

```
1. User logs in
2. Backend creates access token (15m) + refresh token (7d)
3. Refresh token stored in Valkey with 7d TTL
4. Access token returned to frontend
5. Frontend includes access token in Authorization header
6. Backend validates access token
7. When access token expires:
   - Frontend calls /auth/refresh
   - Backend validates refresh token
   - Backend creates new access token + new refresh token
   - Old refresh token revoked
   - New tokens returned
8. When refresh token expires:
   - User must login again
```

### Token Storage

#### Frontend
- Access token: Memory (React state)
- Refresh token: HTTP-only cookie (cannot be accessed by JS)

#### Backend
- Refresh tokens: Valkey with user ID as key
- Session metadata: User ID, device info, IP address

## OAuth Providers

### Supported Providers
- Google
- Apple
- Facebook
- GitHub
- TikTok

### Provider Configuration
```typescript
const providers = {
  google: {
    clientId: process.env.GOOGLE_CLIENT_ID,
    clientSecret: process.env.GOOGLE_CLIENT_SECRET,
    authorizationUrl: 'https://accounts.google.com/o/oauth2/v2/auth',
    tokenUrl: 'https://oauth2.googleapis.com/token',
    userInfoUrl: 'https://www.googleapis.com/oauth2/v3/userinfo',
    scope: 'openid email profile'
  },
  // ... other providers
};
```

### OAuth Flow
1. Frontend redirects to provider authorization URL
2. User authenticates with provider
3. Provider redirects back with authorization code
4. Backend exchanges code for access token
5. Backend fetches user profile from provider
6. Backend creates/updates user account
7. Backend creates session
8. Frontend receives session tokens

## MFA (Multi-Factor Authentication)

### TOTP-based MFA
- **Algorithm:** TOTP (RFC 6238)
- **Issuer:** Hakawi
- **Digits:** 6
- **Period:** 30 seconds
- **Secret:** Base32 encoded, stored encrypted

### Recovery Codes
- **Count:** 10 codes
- **Format:** Alphanumeric, hyphen-separated
- **Storage:** Encrypted in database
- **Usage:** One-time use

### MFA Flow
1. User enables MFA in settings
2. System generates TOTP secret and recovery codes
3. User scans QR code with authenticator app
4. User verifies first TOTP code
5. System stores encrypted secret
6. On login:
   - User enters password
   - If MFA enabled, prompt for TOTP code
   - Validate TOTP code
   - Create session

### MFA Enforcement
- **Optional:** User can enable/disable
- **Admin enforcement:** Admin can require MFA for sensitive operations
- **Super admin:** Always required

## Password Authentication

### Hashing
- **Algorithm:** bcrypt
- **Rounds:** 12
- **Salt:** Auto-generated by bcrypt

### Password Policy
- **Minimum length:** 8 characters
- **Maximum length:** 128 characters
- **Requirements:**
  - At least one uppercase letter
  - At least one lowercase letter
  - At least one number
  - At least one special character

### Password Reset
1. User requests password reset
2. System generates reset token (valid 1 hour)
3. System sends reset email
4. User clicks reset link
5. User enters new password
6. System validates reset token
7. System updates password hash
8. System invalidates all sessions

## Session Security

### Session Creation
- **IP address:** Logged
- **User Agent:** Logged
- **Device info:** Extracted and stored
- **Location:** Approximate location from IP

### Session Validation
- Token signature verification
- Expiration check
- Revocation check
- IP address consistency (optional)
- User agent consistency (optional)

### Session Revocation
- **Single session:** Revoke specific refresh token
- **All sessions:** Revoke all user's refresh tokens
- **Admin action:** Admin can revoke user sessions

### Session Limits
- **Max concurrent sessions:** 5 per user
- **Session cleanup:** Expired sessions cleaned daily

## Security Measures

### Token Security
- Signed with strong secret (256-bit)
- Short expiry (15 minutes)
- Refresh token rotation
- Secure transmission (HTTPS only)

### Cookie Security
- HTTP-only flag
- Secure flag (HTTPS only)
- SameSite: Strict
- Path: `/`
- Domain: Configurable

### Brute Force Protection
- Rate limiting on login endpoints
- Account lockout after 5 failed attempts
- Progressive delay after failed attempts
- CAPTCHA after repeated failures

## Error Handling

### Authentication Errors
- `INVALID_CREDENTIALS` - Wrong email/password
- `ACCOUNT_LOCKED` - Too many failed attempts
- `MFA_REQUIRED` - MFA code needed
- `TOKEN_EXPIRED` - Access token expired
- `TOKEN_INVALID` - Malformed or invalid token
- `SESSION_REVOKED` - Session was revoked

### Error Response Format
```json
{
  "error": "AUTH_FAILED",
  "message": "Invalid credentials",
  "code": "INVALID_CREDENTIALS",
  "statusCode": 401
}
```
