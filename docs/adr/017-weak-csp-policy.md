# ADR 017 — Content-Security-Policy: `unsafe-inline` removed from `script-src` via nonce

- **Status:** Accepted
- **Date:** 2026-11-09
- **Supersedes:** ADR 017 — Content-Security-Policy: `unsafe-inline` and `unsafe-eval` removed from bootstrap script (previous version)
- **Related:** `backend/src/main.ts:26`, `frontend/src/app/layout.tsx`,
  `frontend/src/app/layout.tsx:64-79`, `frontend/src/middleware.ts`,
  `frontend/src/lib/csp.ts`, `frontend/next.config.ts`,
  `frontend/public/js/preference-bootstrap.js`

## Context

The API set `Content-Security-Policy` with `script-src 'self' 'unsafe-inline' 'unsafe-eval'`
(`backend/src/main.ts:26`). The frontend Next.js app set the same via `next.config.ts`
headers. The root layout injected a bootstrap script via `dangerouslySetInnerHTML`
(`frontend/src/app/layout.tsx:74`), which required `'unsafe-inline'`. Next.js itself emits
inline scripts for hydration and the React Server Component runtime, which also require
`'unsafe-inline'` under the current static rendering model.

A CSP that allows `unsafe-inline` permits an attacker who can inject any script tag to run
arbitrary JavaScript. `'unsafe-eval'` permits `eval()`, `new Function()`, and
`setTimeout(string)` — classic XSS escalation primitives.

## Decision

**`unsafe-eval` is removed entirely** — in all environments, development included. Neither React
nor Next.js calls `eval()` in production, and React's development debug hooks do not justify
keeping an XSS escalation primitive in the policy.

**`unsafe-inline` is removed from `script-src` entirely.** The bootstrap script that resolves
theme and locale before first paint has been moved to an external file
(`/js/preference-bootstrap.js`), loaded with a plain `<script src>`. Because it is same-origin,
it is covered by `'self'` and needs no `unsafe-inline` allowance.

Next.js App Router's own injected runtime scripts (hydration, React Server Component payload)
are now covered by a **per-request nonce** generated by `src/middleware.ts`. The middleware
creates a cryptographically random nonce (16 bytes, base64-encoded via `crypto.randomUUID()`)
and writes `'nonce-<value>'` into `script-src` of the `Content-Security-Policy` header.
Next.js reads that nonce back from the header via `getScriptNonceFromHeader` and applies it to
its own inline scripts automatically. An attacker cannot guess the nonce and inject a script
with a matching `nonce` attribute.

## Changes

**`frontend/public/js/preference-bootstrap.js`** (new): the bootstrap script as a static external
file. Same content as the old inline constant, same inputs (localStorage values validated against
a closed allowlist: `"dark"`/`"light"`, `"ar"`/`"en"`).

**`frontend/src/app/layout.tsx`**: replaces
`<script dangerouslySetInnerHTML={{ __html: PREFERENCE_BOOTSTRAP_SCRIPT }} />` with
`<script src="/js/preference-bootstrap.js" defer />`. Removes the `PREFERENCE_BOOTSTRAP_SCRIPT`
import.

**`frontend/src/lib/csp.ts`** (new): `buildCsp(nonce)` function that assembles the full CSP
header with `'nonce-${nonce}'` in `script-src`. Also exports `computeApiOrigin()`.

**`frontend/src/middleware.ts`** (new): generates a per-request nonce via `crypto.randomUUID()`,
calls `buildCsp(nonce)`, and sets the `Content-Security-Policy` response header. Matches all
routes except `_next/static`, `_next/image`, `favicon.ico`, and files with extensions.

**`frontend/next.config.ts`**: CSP removed from static `headers()` — the middleware sets it
per-request instead. Non-CSP security headers (X-Content-Type-Options, Referrer-Policy,
X-Frame-Options, Strict-Transport-Security) remain.

**`backend/src/main.ts:26`**: `unsafe-eval` removed from the API's CSP. `script-src` now reads
`'self'` only.

## Consequences

**Resolved risk:** `'unsafe-eval'` no longer permits `eval()` / `new Function()` exploitation in
any environment, on either the API or the frontend. `'unsafe-inline'` no longer permits any
script injection — our bootstrap script is external (covered by `'self'`) and Next.js's runtime
scripts carry a per-request nonce.

**Remaining risk:** `'unsafe-inline'` remains in `style-src` for Next.js's injected styles.
Styles cannot exfiltrate the session cookie or run JavaScript, so this is an acceptable residual.
`default-src 'self'` and `connect-src 'self'` still limit data exfiltration.

**Mitigation outside this ADR:** all user-supplied HTML passes through `sanitize-html.ts`
before rendering.

---

## Addendum

The CSP is now fully nonce-based for scripts. `script-src 'self' 'nonce-<value>'` covers both
our external bootstrap file (via `'self'`) and Next.js runtime scripts (via the nonce). No
`unsafe-inline` remains in `script-src` anywhere in the application.
